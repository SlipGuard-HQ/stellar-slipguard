SlipGuard was already a Stellar project before this update: the contracts are written against `soroban-sdk` 26 with `#![no_std]` and the `wasm32v1-none` target, settlement is gated by dual `Address::require_auth()` checks, deadlines are read from `env.ledger().timestamp()`, order identity is a SHA-256 hash of `ScVal` XDR computed with `env.crypto().sha256()`, state lives in TTL-extended Soroban storage, funds move over the SEP-41 token interface including the Stellar Asset Contract, the SDK and solver bot speak only to Stellar RPC (`simulateTransaction`, `assembleTransaction`, `sendTransaction`, `getTransaction`, `getEvents`, `getLatestLedger`), and deployment is done with the `stellar` CLI. The problem was never the code; it was the repository around it. The most conspicuous artifacts were a script whose only purpose was to generate an issue backlog labelled with points (`difficulty: trivial 100pts`, `wave-ready`) and three issue templates named "Wave: High (200 pts)", a scattering of EVM vocabulary in a Soroban codebase (`GAS_COST`, "gas cost", "ERC-20 style allowance", a `Keccak`-style hashing comment when the contract actually uses SHA-256, and "MEV-resistant" in the package description), and the complete absence of any page that mapped a Stellar or Soroban primitive to the code depending on it. A reviewer skimming the project saw a points generator and EVM terminology with Soroban somewhere underneath, and this update removes that impression rather than changing any behaviour.

On the documentation side, the README now opens with the Soroban implementation and carries a twelve-row table of Stellar and Soroban primitives, the file that depends on each, and what would fail without it, replacing the previous generic order-flow prose and the "Wave issue backlog" section. A new page, `docs/06-stellar-integration.md`, goes further: it maps primitives across the contract, client and operations layers, states explicitly what is deliberately absent from the design, and is wired into the sidebar and both documentation indexes. The three points-based issue templates were deleted and replaced by `soroban_contract_issue.md`, `stellar_integration_issue.md` and `starter_issue.md`, each requiring a "Stellar surface" section that names the relevant interface (`require_auth`, TTL extension, `ScVal` hashing, SEP-41/SAC, `env.ledger()`, RPC or the CLI), and the pull request template gained the same section plus a check against EVM terminology. `CONTRIBUTING.md` dropped its Wave points and sprint rules in favour of rules about what must be updated when a change touches auth, storage and TTL, `contracttype` encoding, SEP-41 calls, RPC or the `stellar` CLI, with a list of terms to avoid; `SECURITY.md` extended its in-scope list to cover authorization-entry replay, trust in the ledger clock, archival or TTL weakening, confusion between the SAC and the test `MockToken`, and network-passphrase mistakes. `scripts/create-wave-issues.sh` became `scripts/create-stellar-backlog.sh`, which issues no points and sets no sprint state: the `wave-ready` label and the three `difficulty: * 100pts` labels were removed and deleted from the repository, replaced by the standard `enhancement`, `bug`, `documentation` and `good first issue` labels plus a `testing` label alongside the existing `area:` labels, and all fifteen backlog issues now name the Stellar interface they touch, with the existing seventeen issues relabelled so the tracker carries no Wave remnants.

In code and tooling, the EVM vocabulary was removed at its source. The solver's `GAS_COST` environment variable is now `TX_COST`, and the `gasCost` field became `txCost` across `packages/solver-bot/src/config.ts`, `evaluator.ts`, `index.ts` and the evaluator tests; the semantics are unchanged, still an estimate of the fill's total transaction cost in buy-token units, but now explicitly described as the 100-stroop Stellar base fee plus the Soroban resource fee, and the documentation and diagrams were updated to match. Contract doc comments that spoke of an "ERC-20 style allowance" now refer to the SEP-41 allowance, and the `Keccak` reference in `contracts/router/src/types.rs` was replaced with an accurate description of `ScVal` XDR hashed by `env.crypto().sha256()`; the remaining mentions of "allowance" are only the SEP-41 function names the mock token implements. Package metadata no longer claims to be "MEV-resistant" or to run a "keeper", describing the project instead as settled by Soroban contracts on Stellar and run by a solver that watches Stellar RPC events. The deployment path changed materially: `scripts/deploy.sh` now resolves real Stellar Asset Contracts with `stellar contract asset deploy` when `SELL_ASSET` and `BUY_ASSET` are set (`native` or `CODE:ISSUER`), treats setting only one of the two as an error by design, and falls back to explicit, output-labelled test-only `MockToken` instances when neither is set, replacing the previous behaviour of always deploying two mock tokens before the router. `deployments/README.md` now states that the record is network-scoped and shows the SAC command. Contract behaviour, storage layout, error codes and the ABI are untouched: there is no migration, no new entry point and no change to settlement order. Added files are `docs/06-stellar-integration.md`, the three new issue templates, `scripts/create-stellar-backlog.sh` and this file; rewritten or substantially edited are `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `.env.example`, the PR template, the issue template config, `scripts/deploy.sh`, all five original docs pages plus the docs index, README and VitePress config, `deployments/README.md`, the four solver-bot source and test files, both package manifests, and doc comments in the router and mock-token contracts; deleted are the three `wave_*_issue.md` templates and `scripts/create-wave-issues.sh`. Operators only need to act on two things: rename `GAS_COST` to `TX_COST` in any existing `.env`, since an unrenamed variable silently falls back to `0` and makes the bot more willing to submit marginal fills, and be aware that the deploy script now has a SAC mode.

Verification was run on this workspace with Node 24.22.2 and pnpm 12.16.1: `pnpm build:packages`, `pnpm lint:packages`, `pnpm test:packages` (19 SDK tests and 15 solver-bot tests) and `pnpm exec prettier --check .` all pass, `pnpm docs:build` passes in 23.4s with dead links treated as errors, which is the meaningful link check for the new page, and `bash -n` passes on both scripts. The deploy script was exercised in dry-run mode for all three cases, producing the mock plan, resolving both SACs, and correctly exiting 1 when only one asset was supplied, and the backlog script prints eight labels and fifteen issues in dry run. The Rust checks, `cargo fmt`, `cargo clippy` and `cargo test`, could not be run because no Rust toolchain is installed here; the Rust edits are doc comments only, so `cargo test --all` should still be run somewhere with Rust and the `wasm32v1-none` target before relying on CI. Two known gaps remain and are stated rather than hidden: the contracts are unaudited and testnet-only, and the checked-in `deployments/testnet.json` still records demo `MockToken` ids from the earlier deployment, so re-running the script in SAC mode would make the checked-in evidence match the new default path. Separately, the untracked `package-lock.json` is a leftover from an earlier npm install in a pnpm project and is unrelated to this update. For the appeal itself, the strongest single point is that the SDK and the contract share a golden intent-hash vector, so an off-chain hash and `get_intent_hash` must agree or the build fails, which is only meaningful on Soroban because it depends on `ScVal` encoding; the second is that `contracts/mock_token` is test infrastructure implementing `soroban_sdk::token::TokenInterface` so the contract suite can settle without a network, not evidence of an ERC-20 port. There is no Solidity, no EVM bytecode, no `msg.sender`, no chain-abstraction layer and no off-chain settlement path anywhere in the repository: a fill only happens as a Soroban contract invocation.
