# 4. Developer guide

## Requirements

| Tool | Version | Notes |
| --- | --- | --- |
| Rust | stable, 1.84 or newer | `rust-toolchain.toml` pins the channel, components and target |
| `wasm32v1-none` target | any | The only WASM target the Soroban runtime supports |
| Node | 20 or newer | CI runs 20 and 22 |
| pnpm | 12 | `pnpm-workspace.yaml` uses pnpm 12's `allowBuilds` |
| Stellar CLI | recent | Only needed to deploy |

```bash
rustup target add wasm32v1-none
pnpm install
```

## Repository layout

```
contracts/router        SlipGuardRouter: hashing, cancellation, settlement
contracts/mock_token    SEP-41 token used by the test suite
packages/sdk            @slipguard/sdk: build, hash and submit intents
packages/solver-bot     @slipguard/solver-bot: reference keeper daemon
scripts/deploy.sh       Deploys and initializes in dependency order
scripts/create-wave-issues.sh  Creates the Wave issue backlog in one run
docs/                   This documentation set
```

The root `Cargo.toml` is the Rust workspace; the root `package.json` and
`pnpm-workspace.yaml` are the JavaScript workspace. There is deliberately no
`contracts/Cargo.toml`, because a manifest there would create a nested workspace
and shadow the root one.

## Commands

```bash
pnpm test              # cargo test --all, then both packages' tests
pnpm lint              # build, typecheck, prettier --check, cargo clippy -D warnings
pnpm build:contracts   # cargo build --target wasm32v1-none --release
pnpm build:packages    # tsc for both packages, SDK first (topological)
pnpm format            # prettier --write

cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test --all
```

`pnpm build:packages` must run before `pnpm lint:packages` on a clean checkout:
the solver bot resolves `@slipguard/sdk` through its built `dist` types. The root
`lint` script does this for you.

The compiled contracts land in `target/wasm32v1-none/release/` as
`slipguard_router.wasm` and `slipguard_mock_token.wasm`.

## Testing conventions

- Contract tests live in `contracts/router/src/test.rs`. They deploy the router
  and two mock tokens, and drive them through the generated clients with
  `env.mock_all_auths()`. Error assertions go through `assert_contract_error`,
  which matches the typed `SlipGuardError` returned by the `try_*` client.
- A golden hash vector is asserted on both sides:
  `test_intent_hash_matches_sdk_reference_vector` in Rust and
  `"matches the contract's reference hash vector"` in TypeScript. If you change
  the encoding, both will fail until you update them together.
- Pure logic (hashing, encoding, profitability math) is kept free of I/O so it
  can be unit tested without a network.

A full test run leaves a `contracts/router/test_snapshots/` directory. It is
generated by `soroban-sdk` testutils and is gitignored.

## Contract entry points

| Function | Auth | Returns |
| --- | --- | --- |
| `init(admin)` | `admin` | `Result<(), SlipGuardError>` |
| `get_intent_hash(intent)` | none | `BytesN<32>` |
| `cancel_intent(intent)` | `intent.trader` | `Result<(), SlipGuardError>` |
| `execute_intent(solver, intent, actual_buy_amount)` | `solver` and `intent.trader` | `Result<FillReceipt, SlipGuardError>` |
| `get_intent_status(intent_hash)` | none | `IntentStatus` |
| `get_fill_receipt(intent_hash)` | none | `Option<FillReceipt>` |
| `is_nonce_used(trader, nonce)` | none | `bool` |
| `get_admin()` | none | `Option<Address>` |

Errors, the settlement order and the fee math are documented in
[Protocol mechanics](./02-protocol-mechanics.md).

## SDK reference

```ts
import {
  IntentBuilder,
  SlipGuardClient,
  IntentStatus,
  hashIntent,
  serializeIntent,
  deserializeIntent,
  NETWORKS,
} from "@slipguard/sdk";
```

### Building an intent

`IntentBuilder` validates as you build. Addresses must be valid Stellar strkeys,
amounts must be positive integers, basis points must be within `[0, 10000]`, and
`build()` refuses a deadline that is not in the future.

| Method | Notes |
| --- | --- |
| `setTrader(address)` | Required. |
| `setPair(sellToken, buyToken)` | Required. Must differ. |
| `setAmounts(sell, minBuy)` | Required. Accepts `bigint`, integer `number` or numeric `string`. |
| `setSlippageBps(bps)` | Required. Integer within `[0, 10000]`. |
| `setSolverFeeBps(bps)` | Optional, defaults to `0`. |
| `setDeadline(secondsFromNow, now?)` | Deadline relative to now. `now` is overridable for tests. |
| `setDeadlineTimestamp(deadline)` | Absolute unix seconds. |
| `setNonce(nonce)` | Optional, defaults to the current millisecond timestamp. |
| `build(now?)` | Validates and returns `TraderIntent`. Throws `IntentValidationError`. |

```ts
const intent = new IntentBuilder()
  .setTrader(traderPublicKey)
  .setPair(xlmContractId, usdcContractId)
  .setAmounts(1_000_000_000n, 9_500_000n) // 10.0 XLM, floor of 9.5 USDC
  .setSlippageBps(50)
  .setSolverFeeBps(10)
  .setDeadline(600)
  .setNonce(1n)
  .build();
```

### Hashing and serialisation

```ts
hashIntent(intent);          // hex SHA-256, identical to get_intent_hash on chain
intentDigest(intent);        // the same digest as a Buffer
intentToScVal(intent);       // the canonical xdr.ScVal encoding

serializeIntent(intent);     // JSON with bigints as strings
deserializeIntent(json);     // inverse, which validates
```

`serializeIntent` is safe to send through a JSON feed. `deserializeIntent` is
the entry point for untrusted data and throws `IntentValidationError` rather
than a `TypeError`.

### Reading and writing with the client

```ts
const client = new SlipGuardClient({
  contractId: "C...",
  ...NETWORKS.testnet,
  publicKey: traderPublicKey,
});
```

| Method | Purpose |
| --- | --- |
| `hashIntent(intent)` | Local hash, no RPC. |
| `getIntentHash(intent, publicKey?)` | Simulates `get_intent_hash` and returns hex. |
| `getIntentStatus(intent, publicKey?)` | Simulates `get_intent_status` and returns an `IntentStatus`. |
| `simulateRead(operation, publicKey?)` | Runs any read-only operation and returns the raw `xdr.ScVal`. |
| `buildExecuteIntentOperation(solver, intent, actualBuyAmount)` | The `execute_intent` operation. |
| `buildCancelIntentOperation(intent)` | The `cancel_intent` operation. |
| `prepareExecuteIntent({ solver, intent, actualBuyAmount, fee?, authEntries? })` | Simulates, assembles, signs and returns a `Transaction`. |
| `submitTransaction(transaction, timeoutMs?)` | Sends and polls for ledger inclusion. |
| `poll(hash, timeoutMs?)` | Polls an already-submitted hash. |

Reads are simulations, which need a funded source account you pass as
`publicKey`. Writes are simulated, assembled, signed and polled.

### Passing the trader's authorization

`prepareExecuteIntent` accepts `authEntries`. Without them it uses the entries
produced by simulation, which only works when the trader is present to sign at
fill time. With them, you hand over the pre-signed entry and the fill can happen
while the trader is offline.

The solver bot reads these from the feed as a base64
`SorobanAuthorizationEntry` and passes them straight through.

### Network presets

```ts
NETWORKS.testnet;   // { rpcUrl, networkPassphrase }
NETWORKS.futurenet;
NETWORKS.mainnet;
```

Every field is overridable. Treat the mainnet preset as a default to replace
with your own RPC provider.

## Calling the contract directly

If you are not using the SDK, the pattern is the same at the XDR level. The
intent is an `ScVal` map with sorted symbol keys, which is why the SDK's
`intentToScVal` is the piece worth reusing even if you write your own client.

**Read:** build a transaction with the operation, call `simulateTransaction`, and
read `result.retval`. `get_intent_hash` returns `scvBytes`, `get_intent_status`
returns `scvU32`.

**Write:** build, simulate, assemble with `rpc.assembleTransaction`, sign, then
`sendTransaction` and poll `getTransaction` until the status is `SUCCESS` or
`FAILED`. Auth entries live on the operation, so to supply your own you override
`result.auth` from the simulation before assembling.

## Solver bot configuration

Every value is read from the environment by `loadConfig`, which validates
formats and throws `ConfigError` on anything malformed.

| Variable | Required | Default | Notes |
| --- | --- | --- | --- |
| `STELLAR_NETWORK` | no | none | `testnet`, `futurenet` or `mainnet`. Fills in the RPC URL and passphrase. |
| `SOROBAN_RPC_URL` | yes\* | from preset | \*Required when `STELLAR_NETWORK` is unset. |
| `NETWORK_PASSPHRASE` | yes\* | from preset | \*Same condition. |
| `ROUTER_CONTRACT_ID` | yes | none | Must match `C[A-Z2-7]{55}`. |
| `SOLVER_SECRET_KEY` | yes | none | Must match `S[A-Z2-7]{55}`. Never commit this. |
| `INTENT_FEED_URL` | no | none | JSON array of intents, or of `{ intent, traderAuthEntry }`. |
| `POLL_INTERVAL_MS` | no | `5000` | Positive integer. |
| `START_LEDGER` | no | tip of the chain | First ledger scanned for router events. |
| `MIN_PROFIT` | no | `0` | Minimum net profit, in buy token units. |
| `GAS_COST` | no | `0` | Estimated transaction cost, in buy token units. |
| `MAX_FEE_STROOPS` | no | `100000` | Transaction fee ceiling. |
| `TX_TIMEOUT_MS` | no | `60000` | How long to wait for ledger inclusion. |
| `TOKEN_PRICES` | no | `{}` | JSON object of token contract id to USD price. |
| `LOG_LEVEL` | no | `info` | `debug`, `info`, `warn` or `error`. |
| `DRY_RUN` | no | `false` | Evaluate and log without submitting. |
| `ALLOW_HTTP` | no | `false` | Permits plain HTTP RPC endpoints for local sandboxes. |

See [`.env.example`](../.env.example) for a copy-pasteable template.

## Deploying

`scripts/deploy.sh` deploys in dependency order: the router first, then
`init(admin)`, then the demo SEP-41 tokens, then optional demo balances. It
writes every resolved id to `.deploy/contracts.<network>.env` and prints a
copy-pasteable summary.

```bash
pnpm build:contracts
DRY_RUN=true ./scripts/deploy.sh              # print the plan
./scripts/deploy.sh                           # deploy to testnet
NETWORK=mainnet DEPLOY_MOCK_TOKENS=false ./scripts/deploy.sh
```

Prerequisites: the `stellar` CLI on `PATH`, and an identity configured with
`stellar keys generate <name>`, or `SOURCE` pointing at one that exists.

A previously deployed testnet set is checked in at
[`deployments/testnet.json`](../deployments/testnet.json), so you can point the
solver bot and the SDK at working contract ids before running a deployment of
your own.

The script creates new contracts on every run. It does not upgrade existing
ones, and it will not overwrite a deployment on a different network because the
output file is network-scoped.

## The Wave issue backlog

```bash
DRY_RUN=true ./scripts/create-wave-issues.sh   # print the plan
./scripts/create-wave-issues.sh                # create labels and issues
```

It creates the labels (`wave-ready`, `difficulty: *`, `area: *`) and the issue
backlog, each with a summary, scoped acceptance criteria and a tech stack line.
Labels are created with `--force`, so re-running is safe for labels. Issues are
not de-duplicated, so run it once.

## CI

`.github/workflows/ci.yml` runs two jobs. `contracts` checks formatting, runs
clippy with warnings as errors, runs the contract tests, and builds the release
WASM. `packages` installs with `--frozen-lockfile`, checks formatting, builds,
typechecks and tests, on Node 20 and 22.

`.github/workflows/lint.yml` repeats the lint half with `--all-features` on the
Rust side.

Both workflows assert exactly what `pnpm lint` and `pnpm test` assert locally,
so a green local run predicts a green CI run.

## Contributing

See [CONTRIBUTING.md](../CONTRIBUTING.md) for branch conventions, the Wave
sprint rules, and the coding standards. The short version: no `unwrap()` outside
tests, no floating point in contract math, state written before external calls,
and tests for new behaviour.
